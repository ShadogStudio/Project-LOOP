# Project LOOP — AI 사용 예시

**목적**: 채용/포트폴리오 제출용. Cursor(Composer)를 개발 보조로 쓴 방식과 한계를 정리한다.  
**원칙**: 요구사항·수용 기준·최종 판단·검증은 본인이 한다. AI는 탐색·초안·반복 구현·문서 정리를 가속한다.  
**문서 기준일**: 2026-09-07 · 저장소: https://github.com/ShadogStudio/Project-LOOP

---

## 1. 도구와 협업 규칙

| 항목 | 내용 |
|------|------|
| 도구 | Cursor Agent (Composer), 프로젝트 `.cursor/rules` |
| 규칙 | 문서↔코드 일치, 최소 변경, Commit/Push는 사용자 확인 후, 시크릿·ThirdParty 바이너리 비공개 |
| 커밋 형식 | `[작업유형] 제목` + `-` 상세 리스트 |
| 역할 분담 | 본인: 범위·우선순위·수용/롤백 · AI: 코드 초안·리팩터 제안·버그 조사·문서 초안 |

AI가 “완성했다”고 주장해도, Play 모드·콘솔·문서와 실제 커밋을 대조한 뒤에만 반영한다.

---

## 2. 작업 흐름 (반복)

```text
목표·비목표 명시
  → AI에게 기존 코드/문서 먼저 읽게 함
  → 초안 구현 또는 수정안 제시
  → Unity에서 플레이/로그로 검증
  → 문제면 롤백 또는 범위 축소
  → DEVELOPMENT/CHANGELOG 갱신
  → 커밋 메시지 확인 후 커밋 (푸시는 별도)
```

프롬프트는 **결과물·제약·비목표**를 같이 적는다.  
예: “상점 해금이 던전 입장 후 리셋되면 안 됨. PlayerPrefs 유지. EOS는 건드리지 말 것.”

---

## 3. 대표 사례

### 사례 A — 공개 베이스와 의존성 분리

**문제**  
포트폴리오로 GitHub에 올리려면 상용 아트·SDK 없이도 클론·실행되어야 한다.

**판단**  
코어는 자체 구현. 던전·저장·온라인은 인터페이스 + 기본/Null 구현. 구매 에셋은 `Assets/ThirdParty` + `.gitignore`.

**AI 역할**  
폴더/스텁 골격, `IDungeonGenerator` / `IOnlineServices` / `ISaveService` 초안, README·DESIGN의 공개 vs 로컬 표 작성.

**본인 검증**  
ThirdParty 없이 Town→Dungeon 플레이, 빌드 설정 씬, ignore 규칙, 문서에 상용 팩 목록을 남기지 않음.

**결과**  
클론만으로 코어 루프 실행 가능. 온라인은 Null 스텁으로 v2+ EOS 자리만 확보.

---

### 사례 B — 마을↔던전 루프 · 전투 · 상점

**문제**  
“식량·시신” 등 초기 기획이 바뀐 뒤, **마을 거점 + 런 재화 + 최소 전투 + 메타 상점**으로 v1을 고정해야 했다.

**판단**  
플레이스홀더로 루프를 먼저 닫고, 비주얼·EOS는 뒤로 미룬다.

**AI 역할**  
`GameSession`·포탈·Simple 던전 생성기·근접 전투·상점·라벨/HP 오버레이 구현 보조, 커밋 단위 분리 제안.

**본인 검증**  
예치/사망 손실, 적 최소 1마리, 상점 구매 상한, 조작(README)과 실제 입력 일치.

**결과**  
커밋 단위로 루프 → 전투 → 상점 → UX 피드백이 쌓인 플레이 가능 빌드.

---

### 사례 C — 메타 저장 유실 버그

**문제**  
마을에서 활력/힘을 산 뒤 던전에 들어가면 보너스가 초기화되는 경우가 있었다.

**판단**  
씬 전환 타이밍·세션 생성 순서·저장 시점을 의심. EOS/새 저장 시스템이 아니라 로컬 저장 경로를 고친다.

**AI 역할**  
`EnsureExists`, 원자적 `SaveMeta`, 포탈 전환 전 persist, 플레이어 스탯 적용 경로 추적·패치.

**본인 검증**  
구매 → 던전 입장 → HP/데미지 유지 → 재실행 후 해금 유지.

**결과**  
메타가 PlayerPrefs에 안정적으로 남음. “증상 → 원인 가설 → 최소 패치 → 재현 확인” 흐름을 AI와 분담.

---

### 사례 D — 외형 바인딩 시도 후 롤백

**문제**  
Synty 등 로컬 에셋을 플레이스홀더에 붙이다가 Instantate/캐스팅 오류, 마을 바닥 콜라이더 이슈 등이 발생했다.

**판단**  
포트폴리오 공개 베이스의 안정성이 우선. 바인딩은 보류하고 게임플레이 코드를 마지막 안정 커밋 기준으로 되돌림.

**AI 역할**  
바인딩 초안·에러 조사. 이후 사용자 지시에 따라 롤백·ThirdParty 정리 보조.

**본인 검증**  
플레이 가능 상태 복구. 문서에서 “에셋 연결 완료”로 과대 표기하지 않음.

**결과**  
실패를 숨기지 않고 **범위 축소·롤백**한 사례. AI 산출물을 무조건 머지하지 않는 기준을 보여 줌.

---

### 사례 E — 문서와 실제 상태 정렬

**문제**  
옛 문서에 미구현(EOS 본연동, DA 본연동, 식량 루프 등)이 남아 있거나 “1단계 골격만”처럼 과소 표기되어 있었다.

**판단**  
면접관이 README만 봐도 현재 빌드와 맞게. 안 된 것은 Next로, 된 것만 Completed.

**AI 역할**  
코드·커밋 대조 후 README / DESIGN / DEVELOPMENT / CHANGELOG / 폴더 README 재작성.

**본인 검증**  
문서의 “구현됨” 목록이 Play 가능한 기능과 1:1인지 확인.

**결과**  
문서가 현재 v1(루프·전투·상점·피드백)과 일치.

---

## 4. 프롬프트 작성 요령 (실제 패턴)

좋은 예:

- “기존 `GameSession` 패턴을 유지하고, 새 매니저를 만들지 말 것.”
- “커밋/푸시는 하지 말고 코드만 수정.”
- “ThirdParty 바이너리는 Git에 추가하지 말 것.”
- “미구현을 완료로 문서에 쓰지 말 것.”

나쁜 예:

- “알아서 포트폴리오 수준으로 완성해줘.” (범위·수용 기준 없음)
- “EOS까지 다 붙여줘.” (v1 비목표와 충돌)

## 5. 효과와 한계

| 효과 | 한계 |
|------|------|
| 인터페이스·스텁·반복 CRUD성 구현 속도 | Unity 씬/프리팹 참조 깨짐은 Play로만 확실히 잡힘 |
| 버그 재현 경로 탐색 | 잘못된 전제면 틀린 패치를 빠르게 양산할 수 있음 |
| 문서·커밋 메시지 초안 | 측정 수치·미구현 기능을 지어내지 않도록 본인 검열이 필요 |
| 규칙 파일로 협업 습관 고정 | 규칙이 없으면 범위가 쉽게 비대화됨 |
